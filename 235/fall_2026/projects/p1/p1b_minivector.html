Overview

In Part A, you built MiniVector, an int-only stand-in for std::vector<int>. In Part B, you convert that exact class into a template, MiniVector<T>, so that the same array can hold int, double, std::string, or a class type like Rectangle — without writing the growth, copying, or ownership logic more than once. Every design decision you already made in Part A (capacity starts at 2, never 0; reserve() owns all allocate/copy/free logic; the allocate-before-release order in operator=) carries over unchanged. Most of the conversion is mechanical: every out-of-class function definition in MiniVector.tpp gains a template <typename T> line, and the element type int becomes T. But two things are genuinely new conceptual material, not just mechanical substitution: the reason the implementation moves out of a .cpp file and into a .tpp file (explained below), and the type requirements a generic T must satisfy that a fixed type like int never had to (see the Type requirement note further down).

Why a .tpp file instead of a .cpp file? A template is not compiled the way an ordinary function is. The compiler cannot generate machine code for MiniVector<T>::push_back until it knows what T is, and it only learns that at the point in some other file where you write MiniVector<int> or MiniVector<Rectangle>. That means the compiler needs to see the full body of every template function in every file that uses MiniVector — not just its declaration, the way an ordinary header/.cpp split allows. The convention this project uses, and the one you will see in real C++ codebases, is to put declarations in MiniVector.hpp as usual, put the implementations in a separate file named MiniVector.tpp, and #include "MiniVector.tpp" at the very bottom of MiniVector.hpp (already done for you — see the Skeleton Code section). You still write your code in MiniVector.tpp exactly the way you'd write a .cpp file; you just never #include or compile that file directly yourself.

You are given MiniVector.hpp (the complete interface, reproduced below), MiniVectorTest.cpp (the complete self-check harness), and Rectangle.hpp/Rectangle.cpp (the class from Day 1, used unchanged here to prove your template works for a type you didn't design around). MiniVector.tpp (also reproduced below) has every required function stubbed out with a TODO. Unlike Part A, where you created MiniVector.cpp yourself, Part B provides the implementation-file structure so that you can focus on template syntax and generic types.

Scope note. As in Part A, this project intentionally has a reduced interface — no front() or back(). The new requirement in Part B is entirely about genericity:

Type requirement. This simplified implementation requires T to support default construction, copying, copy assignment, and destruction. A production std::vector manages raw, uninitialized storage separately from the objects constructed in it, so it can support some element types that do not meet all of these requirements (a type with no default constructor, for instance); MiniVector cannot, because new T[capacity] default-constructs every capacity slot up front. int, double, std::string, and Rectangle (given, from Day 1) all satisfy MiniVector's requirements. This implementation provides no exception guarantee if copying or assigning a T throws mid-operation — that is an advanced topic beyond this project's scope.

Task A — Construction and destruction (5 pts)

Implement the default constructor, the count constructor, and the destructor — the same three functions as Part A's Task A, now templated on T.

The default constructor allocates a starting array of capacity 2, exactly as in Part A, using new T[2]{} rather than new T[2]. new T[2]{} value-initializes every allocated element. For Rectangle, both new Rectangle[2] and new Rectangle[2]{} call its user-provided default constructor for each slot — the braces make no difference here. The braces are especially significant for built-in types such as int, whose elements become zero rather than indeterminate: new int[2] (no braces) would leave both slots holding whatever garbage bytes happened to already be at that memory address, while new int[2]{} guarantees zero. The reason to always write the braced form here is that it gives one consistent value-initialization rule for every T, rather than a rule that matters for some types and does nothing for others. Rectangle's default constructor happens to set length_ and width_ to 2.0 and 1.0; whatever a type's default constructor does is what a freshly-allocated, not-yet-used MiniVector<T> slot will contain.

MiniVector<int> v; // data_ -> [0, 0] size_=0 capacity_=2 MiniVector<int> w(3); // data_ -> [0, 0, 0] size_=3 capacity_=3 MiniVector<Rectangle> r(3); // data_ -> [Rectangle(2.0, 1.0), Rectangle(2.0, 1.0), Rectangle(2.0, 1.0)] size_=3 capacity_=3

The destructor's entire job is delete[] data_; — nothing else, exactly as in Part A. delete[] correctly calls each element's own destructor before freeing the array, whatever T is; you do not write a loop for this.

Task B — Growth and capacity (6 pts)

Implement reserve(std::size_t newCapacity) and push_back(T element) — identical logic to Part A, with int replaced by T throughout, including the parameter and array element type.

reserve(newCapacity): if newCapacity is larger than the current capacity(), allocate a new array of exactly that size. new T[newCapacity] (no trailing {}) is fine here, because the loop below only ever overwrites the first size() slots — the remaining newCapacity - size() slots are spare capacity that no code reads until a later push_back() writes into it first. (For a class type such as Rectangle, every allocated slot is still default-constructed regardless of the braces, since new T[n] always default-constructs class-type elements; for a built-in type such as int, the unused spare slots may hold uninitialized garbage, which is harmless precisely because they are outside the logical range.) Then copy the existing size() elements into the new array with a loop (T supports copying, but not necessarily memcpy-style bitwise copying — a std::string or Rectangle element must be copied with operator=, not by copying raw bytes), and free the old array. Otherwise, reserve() does nothing.

v: size=2 capacity=2 [10, 20] v.reserve(10) -> size=2 capacity=10 [10, 20, _, _, _, _, _, _, _, _] v.reserve(1) -> size=2 capacity=10 (no-op: 1 <= capacity())

push_back(T element) should not duplicate reserve()'s logic: when size() == capacity(), call reserve(2 * capacity()), then write element into data_[size_] and increment size_.

push_back(Rectangle(4.0, 5.0)) size=1 capacity=2 push_back(Rectangle(6.0, 7.0)) size=2 capacity=2 push_back(Rectangle(8.0, 9.0)) size=3 capacity=4 <- reserve(4) called: 2 -> 4

Error / throw conditions: none required. Ordinary allocation failure follows new[]'s behavior (std::bad_alloc, not caught here).

Task C — Removal and checked access (5 pts)

Implement pop_back(), clear(), and both overloads of at(std::size_t pos) — identical to Part A, templated on T.

at() must throw std::out_of_range when pos >= size(), exactly like std::vector<T>::at(). pop_back() keeps Part A's contract unchanged: precondition !empty(), undefined behavior (not a throw) if violated, and it must not touch capacity_ or the underlying array beyond decrementing size_. clear() is the same "logical removal only" operation as Part A: set size_ to 0, with no precondition, leaving capacity_ and the array untouched.

v: [10, 20, 30] size=3 capacity=4 pop_back() -> [10, 20] size=2 capacity=4 (capacity unchanged) at(5) -> throws std::out_of_range (5 >= size_) at(1) -> returns 20
A subtlety unique to templates: this differs from std::vector::clear() and std::vector::pop_back(). A standard vector destroys the removed element(s) immediately (calling their destructors) but normally retains its raw allocated capacity. This simplified MiniVector does not separately manage constructed objects and raw storage the way a production vector does, so both functions perform logical removal only: clear() sets size_ = 0, and pop_back() decrements size_ by one, but neither destroys anything — the old T objects remain alive in the allocated array until they are overwritten, the array is reallocated, or the MiniVector itself is destroyed. For int, that's invisible — leftover bytes are just leftover bytes. For a type like std::string, it means a string's heap buffer is still allocated and still owned by that slot; it isn't leaked (the array itself still owns it, and the destructor will eventually free it), but it also isn't doing any useful work in the meantime.

Task D — Rule of Three (9 pts)

Implement the copy constructor and copy-assignment operator, templated on T, using the same allocate-before-release pattern from Part A:

  1. guard against self-assignment (if (this == &other) return *this;)
  2. allocate a temporary new array sized to other.capacity()
  3. copy other's elements into the temporary array, one at a time with operator= (a loop, not memcpy — T may own its own heap memory, as std::string does)
  4. delete[] the old array
  5. install the new pointer, and update size_/capacity_

Why this == &other, not *this == other? this is a pointer to the destination object, and &other is a pointer to the source object. Comparing these addresses asks the correct question: "Are these the same object?" In contrast, *this == other attempts to compare the two objects by value. That expression does not even compile unless MiniVector<T> defines operator== (it doesn't) — and even if value equality were implemented, two different vectors that happen to contain equal elements would not be a self-assignment, so testing value equality would ask the wrong question anyway.

The bug this project is specifically designed to catch: allocating new T[other.size()] instead of new T[other.capacity()]. Both versions report the same, correct capacity() value afterward (you just copy other.capacity_ into your own capacity_ either way) — the bug is that the underlying array is physically too small for the capacity you're claiming. A copy or assignment that only reads back the elements it just copied will never notice. The self-check catches this by push_back()-ing one more element immediately after a copy or assignment, writing into the "slack" between size() and capacity() that should already exist as real, allocated storage:

MiniVector<int> v5(3); // size=3 capacity=3 v5[0]=10; v5[1]=20; v5[2]=30; v5.push_back(40); // size=4 capacity=6 (one doubling; capacity 6, size 4 -- 2 slots of slack) MiniVector<int> v6(1); v6 = v5; // v6 now claims capacity() == 6 v6.push_back(999); // writes into v6's slack slot -- if the underlying array was only // sized to other.size_ (4), this is a heap-buffer-overflow that // AddressSanitizer catches immediately, even though v6.capacity() // itself still (wrongly) reads 6

A deep copy must also be independent in both directions: mutating the copy must never affect the source, and vice versa. This matters even more for MiniVector<Rectangle> than it did for int in Part A — if your copy loop somehow shared storage instead of duplicating it (for instance, by copying the pointer data_ itself rather than looping and copying element by element), the bug would be far more obvious with a class type, since assigning a new Rectangle into one copy would silently overwrite the "original" too.

Error / throw conditions: none required beyond what new[] or a T's own copy assignment might throw; self-assignment (v = v;) must leave v completely unchanged and must not corrupt or leak memory.

Algorithm Reference

Complexity Analysis

Let n = the number of elements pushed. These bounds are unchanged from Part A — templates change what is stored, not how the growth algorithm behaves.

The bounds below count each construction or assignment of one T object as a single element operation. That is exactly accurate for int, and reasonable for a small class like Rectangle. For a general T — a long std::string, say — copying or assigning one element can itself take nonconstant time, so multiply the bounds below by whatever that per-element cost is. In other words, "amortized O(1)" below means amortized O(1) element operations, which is the correct statement for a generic T; it does not mean O(1) wall-clock time regardless of what T is.
ResourceBoundWhy
Time per push_back — amortized O(1) O(1) amortized, O(n) worst case for any single call (element operations) Most calls are O(1): there's room, so it's a write and an increment. The expensive O(n) reallocation happens only at the doubling points, and the total number of element copies caused by all reallocations across n insertions is 2 + 4 + 8 + … < 2n — a geometric sum, so O(n) total, not O(n²). Dividing that O(n) total by the n insertions that caused it gives an amortized cost of O(1) element operations per push_back.
Allocated space O(capacity()) The heap array contains exactly capacity() slots of type T. If capacity grows only through push_back(), capacity remains within a constant factor of size(), so allocated space is O(n) × sizeof(T).

Why templates instead of a separate class per type?

Without templates, supporting MiniVector for both int and Rectangle would mean either writing (and maintaining, and debugging) two nearly identical classes, or something worse like void*-based type erasure. A template is compiled once per type actually used — the compiler generates a distinct MiniVector<int> and a distinct MiniVector<Rectangle>, each type-checked and optimized independently, from the single generic definition you write once. This is the same idea behind every standard-library container you've used (std::vector<T>, std::map<K,V>, and so on).

Concept check (ungraded reflection): The self-check builds MiniVector<int>, MiniVector<double>, MiniVector<std::string>, and MiniVector<Rectangle> in the same program. Roughly how many distinct versions of push_back does the compiler actually generate machine code for? What determines that number?

MiniVector.hpp — do not modify

// File name: MiniVector.hpp, template version
//
// MiniVector: a simplified template vector.
//
// The point of this class (as with std::vector) is to give clients an
// array that can grow. Internally we keep three pieces of state:
//
//   data_      - pointer to a dynamically allocated array of type T on the heap
//   size_      - how many elements are actually "in use" (logical length)
//   capacity_  - how many elements the current allocation can hold
//                before we must reallocate
//
// size_ <= capacity_ always. The gap between them is spare room that lets
// push_back() be fast most of the time (amortized O(1)) instead of
// reallocating on every single insertion.
//
#ifndef MINIVECTOR_HPP
#define MINIVECTOR_HPP

#include <cstddef>

// Type requirement:
// T must support default construction, copying, assignment, and destruction.
template <typename T>
class MiniVector {
public:
  // Creates an empty vector with an allocated array of capacity 2.
  // size() == 0 and capacity() == 2.
  MiniVector();

  // If count > 0, creates a vector containing count value-initialized
  // elements, with size() == capacity() == count.
  // If count == 0, behaves like the default constructor:
  // size() == 0 and capacity() == 2.
  // Marked explicit so that an integer count cannot implicitly convert
  // into a MiniVector<T>.
  explicit MiniVector(std::size_t count);

  // Deep copy: `other`'s elements are duplicated into freshly allocated
  // storage. Modifying one vector must never affect the other.
  MiniVector(const MiniVector& other);

  // Deep-copy assignment. Must correctly handle self-assignment
  // (v = v;) and release any storage this vector previously owned.
  MiniVector& operator=(const MiniVector& other);

  // Releases the heap array owned by this vector.
  ~MiniVector();

  // Bounds-checked element access: throws std::out_of_range if
  // pos >= size(). Prefer this over operator[] when you're not sure
  // the index is valid.
  // MiniVector.tpp includes <stdexcept> for std::out_of_range.
  T& at(std::size_t pos);
  const T& at(std::size_t pos) const;

  // Unchecked element access (like std::vector::operator[]).
  // Passing an out-of-range position results in undefined behavior.
  T& operator[](std::size_t pos);
  const T& operator[](std::size_t pos) const;

  bool empty() const;
  std::size_t size() const;
  std::size_t capacity() const;

  // Ensures capacity() >= newCapacity, reallocating if necessary.
  // Existing elements and size() are preserved.
  // Does nothing if newCapacity <= capacity().
  void reserve(std::size_t newCapacity);

  // Removes all elements. size() becomes 0, but capacity() and the
  // underlying allocation remain unchanged.
  void clear();

  // Appends element to the end. If size() == capacity(),
  // doubles the capacity before inserting.
  void push_back(T element);

  // Precondition: !empty(). Like std::vector::pop_back(), calling this
  // on an empty MiniVector is undefined behavior -- do not add a check,
  // and do not throw. Must not change capacity().
  void pop_back();

private:
  T* data_;
  std::size_t size_;
  std::size_t capacity_;
};

// The template definitions must be visible to every file that uses MiniVector.
#include "MiniVector.tpp"

#endif
