1. Overview

The 24 Game is a classic arithmetic puzzle: you are given a hand of numbers, and your job is to combine all of them — using addition, subtraction, multiplication, and division, and parentheses in any order you like — so that the result is exactly 24. For example, given the hand {1, 2, 3, 4}, one valid combination is 1 * 2 * 3 * 4 = 24. Given {4, 4, 7, 7}, one valid combination is 7 * (4 - 4 / 7) = 24.

In this project, you will progressively build a recursive Make 24 solver in three stages. You will first determine whether a hand can make 24 (Task A), then return one valid expression that proves it (Task B), and finally find every distinct expression the search algorithm can generate (Task C). Every number in the hand must be used exactly once at every stage. This handout walks through the recursive strategy shared by all three tasks and the reference implementation you'll be extending.

2. The Recursive Idea

Think of the hand of numbers as a set of cards on a table. You pick up any two cards, combine them with one arithmetic operation to produce a single new card, and place that new card back on the table in place of the two you removed. The table now has one fewer card than before. You repeat this process until only one card remains: if that final card's value is 24, the original hand can make 24.

This gives a natural recursive definition. Let numsVec be the current hand of numbers.

  • Base case: if numsVec has exactly one element, the hand can make 24 if and only if that element's value is (approximately) 24.
  • Recursive case: if numsVec has two or more elements, try every pair of positions (i, j). For each pair, compute every possible result of combining numsVec[i] and numsVec[j] with +, -, *, or /. Replace the pair with one candidate result at a time, forming a smaller hand, and recurse. If any pair, any operation, and the recursive call on the resulting smaller hand returns true, the whole hand can make 24.
Key idea: the recursion always shrinks the hand by exactly one card per call (two cards go in, one comes out). A hand of n numbers therefore recurses to depth n − 1 before hitting the base case.

Every level combines exactly two numbers into one and passes the smaller hand down to the next call — one edge in the tree per recursive call. The true at the leaf propagates all the way back up through every level of the recursion, short-circuiting any remaining pairs or operations at each level that hadn't been tried yet.

Why remove index j before index i?

Once two positions i < j have been chosen and combined, both must be removed from the working copy of the vector and replaced by the single combined value. A common bug is removing them in the wrong order and changing which value occupies the other selected index. The reference implementation uses a specific trick: 

std::swap(cloneVec[j], cloneVec[size-1]);
cloneVec.pop_back();
// cloneVec now has size-1 elements
std::swap(cloneVec[i], cloneVec[size-2]);
cloneVec.pop_back();

Because j > i, swapping cloneVec[j] to the end and popping it off does not disturb the position of index i — index i is guaranteed to be less than j, so it is untouched by that swap. Only after j has been removed is it safe to swap cloneVec[i] to the (now new) last position and pop it too.

Common mistake: swapping both i and j to the last two positions before popping either one (e.g. swap(i, size-1); swap(j, size-2); pop_back(); pop_back();) looks symmetric but is wrong. Consider {10, 20, 30, 40, 50} with i = 1, j = 4 (the values 20 and 50):
start: {10, 20, 30, 40, 50} swap(i, size-1): {10, 50, 30, 40, 20} // 20 and 50 swap places swap(j, size-2): {10, 50, 30, 20, 40} // index j=4 now holds 40, not 50! pop_back(); pop_back(): {10, 50, 30}
You meant to remove 20 and 50, leaving {10, 30, 40}. Instead the method removes 20 and 40, and 50 — the value you meant to discard — incorrectly survives. The bug is that the second swap targets index j by position, but the first swap already moved a different value into that position. Removing the larger index first, and only then the smaller one (as the reference implementation does), is what keeps both positions valid throughout.

3. Comparing Floating-Point Numbers Safely

All values in this project are stored as double, even though the puzzle is usually played with integers. This matters because division can produce non-integer intermediate results (for example, 4 / 7 in the {4, 4, 7, 7} example above). Two floating-point values that are mathematically equal are not guaranteed to be bit-for-bit equal after a sequence of arithmetic operations, so the code never uses == to compare doubles. Instead it uses a small tolerance: 

const double DELTA = 1e-6;
...
return std::fabs(numsVec[0] - GOAL) <= DELTA;

The same tolerance is used to guard against division by zero. Checking num2 != 0 only rejects a denominator that is exactly zero; a denominator that is merely very close to zero (due to rounding) would still slip through and could blow up into a huge, meaningless value. Comparing against DELTA instead catches both cases: 

if (std::fabs(num2) > DELTA) {
  result.push_back(num / num2);
}

4. Complexity Analysis optional

This section is optional. If you're not ready for it yet, skip ahead to Section 5 — nothing later in the handout depends on the formulas here, and you can always come back once you've started coding.

The lesson that matters here is qualitative, not the formula: each recursive call branches into every pair of positions and every operation on that pair before recursing, so the search explores a branching tree (backtracking) whose size explodes far faster than the size of the hand grows — which is exactly why the 24 Game is traditionally played with a small, fixed hand size (four numbers). The closed-form bound below makes that precise, but deriving it is optional; understanding why the tree explodes is the point.

Let n be the number of values in the hand. At each recursive call on a hand of size k, the algorithm considers every pair of positions (C(k, 2) = k(k−1)/2 pairs) and, for each pair, up to 6 possible results (+, two orders of −, *, and up to two orders of /), before recursing on a hand of size k − 1.

ResourceBoundWhy
Time (worst case — no solution exists) O(3n−1 · n! · (n−1)!)
optional closed-form derivation
The recurrence is T(k) = 6 · C(k,2) · T(k−1) = 3k(k−1) · T(k−1), with T(1) = O(1). Expanding the product from k = 2 to n gives the closed form at left — algebra you're welcome to skip if the qualitative point above is all you need.
Space (auxiliary) O(n2) Because the vectors are copied at successive recursion levels, one active recursion path can hold vectors whose sizes are proportional to n + (n−1) + (n−2) + … + 1 = O(n2), matching the recursion depth of O(n) times O(n) per frame.
Note: for Tasks A and B, this bound is reached when the search must exhaust every possibility; when a solution is found early, the recursion can stop and unwind immediately. Task C is different: because it must collect every required solution, it does not short-circuit and must exhaust the full search space.

5. From Idea to Code

The recursive definition in Section 2 translates into code almost line-for-line. In pseudocode, Task A's make24() looks like this: 

make24(hand):
    if hand has exactly one value:
        return whether that value is approximately 24

    for every pair of positions i < j in hand:
        for every result arithmetic(hand[i], hand[j]) produces:
            build a smaller hand: remove i and j, append the result
            if make24(smaller hand) is true:
                return true

    return false  // no pair, no operation, led to 24

Writing the actual C++ requires translating that pseudocode into working vector manipulation, backtracking, and short-circuiting — that translation, plus the removal-order subtlety worked through in Section 2, is Task A itself. The starter file p3_taskA_skeleton.cpp gives you the function signatures, a self-check main(), and detailed comments describing exactly what each piece of the pseudocode above should do; it does not give you the loops themselves. See Section 6 for what each task's skeleton expects of you, and download your task's starter file from the course page.

Task B — return one expression

Instead of a plain double, each element of the working hand now carries its expression text alongside its numeric value: 

struct Expression_Value {
  std::string expression;
  double value;
};

Combining two elements builds a new Expression_Value whose expression field wraps both operands' text in parentheses (e.g. combining "4" and "(3+(1+2))" with * produces "(4*(3+(1+2)))") and whose value field is the actual arithmetic result. The base case (size == 1) returns that element's expression string if its value is 24, or "" otherwise. The outermost parentheses may be stripped once at the very end for display; the autograder accepts either form. Start from p3_taskB_skeleton.cpp, which gives you the Expression_Value struct and function signatures; both make24() overloads and arithmetic() are left for you to write.

Task C — return every expression

Same idea as Task B, but the base case appends to a std::vector<std::string>& passed by reference instead of returning immediately, and the recursive case never short-circuits on the first success — it keeps exploring every remaining pair and operation. A contains() check before each push prevents the exact same expression string from being recorded twice.

Because the algorithm considers every pair i < j, generates the required arithmetic results for each pair, and follows the specified parenthesization convention, the set of expression strings it can produce for a given hand is well-defined — not a matter of taste. Task C is graded against that exact set (Section 7), so your implementation needs to follow the same construction convention as the reference: always wrap every binary operation in parentheses, and write each operand's leaf text as the plain integer (e.g. "4", not "4.0" or " 4"). You may explore those pairs and candidate results in any order you like — only the final set of strings you collect is checked, not the order you found them in.

What “every distinct expression” means here: Task C is not asking for all mathematically equivalent ways of writing 24. It asks for all distinct expression strings generated by the recursive algorithm and expression-construction rules specified in this project. Two expressions that are mathematically equivalent but structured differently — for instance, by exploiting commutativity to combine the same operands in a different grouping than the reference's traversal would ever produce — are different demands: the second is a harder, open-ended problem this project does not ask you to solve. Task C is an exercise in extending the supplied algorithm to collect everything it can produce, not in enumerating every algebraically distinct way to reach 24.

Start from p3_taskC_skeleton.cpp, which gives you the Expression_Value struct, the contains() helper, and function signatures; both make24() overloads and arithmetic() are left for you to write.

7. How Your Submission Is Graded

Key idea: for Task B, the grader does not compare your returned expression against one fixed “expected” string. Different valid traversals of the search space produce different, equally correct expressions for the same hand — you are not required to reproduce the instructor's exact output. For Task C, individual expressions are validated the same way, but the complete returned set must also match the reference-generated set described below.

Instead, every expression you return is checked against two independent requirements:

  1. It parses as a valid arithmetic expression — integers, + - * /, and parentheses, with no unary minus — and evaluates to 24 within a small floating-point tolerance.
  2. It uses exactly the operands you were given: the same values, the same number of times each. Sorting the integer literals found in your expression and comparing that list to the sorted input hand must give an exact match.

Requirement 2 exists specifically to rule out shortcuts. A submission that just special-cased return "24"; would satisfy requirement 1 for every input, but only satisfies requirement 2 when the input hand actually is {24} itself:

Input handReturned expressionResultWhy
{24} "24" accepted evaluates to 24; operand multiset {24} matches exactly
{1, 2, 3, 4} "24" rejected evaluates to 24, but uses none of the required operands — {24} ≠ {1,2,3,4}
{1, 2, 3, 4} "4*(3+(1+2))" accepted evaluates to 24; uses exactly one 1, one 2, one 3, one 4
{4, 4, 7, 7} "7*(4-4/7)" accepted evaluates to 24; uses exactly two 4s and two 7s
{1, 2, 4} (unsolvable) "" accepted the empty-string “no solution” claim is checked against a hidden reference solver, not taken on faith — here it's correct

For Task C, the bar is higher: the grader computes the exact set of expression strings the reference search algorithm produces for that hand (well-defined by the required pair selection, arithmetic results, and expression-construction rules — see Section 6), strips a single pair of outermost parentheses from every string you return (the same normalization the reference's own main() applies before printing), and requires your normalized set to match the reference's exactly: 

std::vector<std::string> normalized;
for (const std::string& s : student) {
  normalized.push_back(normalize_outer_parentheses(s));
}
std::set<std::string> actual(normalized.begin(), normalized.end());
std::set<std::string> expected(reference.begin(), reference.end());

if (actual == expected) {
  // complete and correct
}

Comparing as sets (rather than vectors) means you may discover the solutions in any order you like — only the final collection matters. Normalizing before comparing also means your returned vector may not contain duplicate strings after that same normalization: two raw strings that differ only by an optional outer pair of parentheses (for example "(7*(4-(4/7)))" and "7*(4-(4/7))") are the same solution, so returning both counts as a duplicate (checked by comparing the size of the normalized vector above to the size of its own set). This design catches every failure mode that matters:

SymptomDetected as
missing a valid solutionnormalized returned set is smaller than the expected set
an invented or malformed expressionfails the per-expression validity check, and/or makes the returned set differ from the expected set
the same solution returned twice (with or without an extra outer paren pair)normalized vector size ≠ normalized set size
solutions found in a different orderaccepted — order is never checked

This is deliberately stricter than Task B: returning just one correct solution to Task C's function signature will not pass, because Task C's contract is to find all of them — otherwise Task C would be indistinguishable from Task B.

Why no unary minus? Every numeric literal appearing in a returned expression must correspond directly to one of the original operands — that's what makes the operand-multiset check in Section 7 unambiguous. Allowing a literal like -3 would raise an unanswerable question for the grader: is that a negative operand, or is it 3 with a unary minus applied? Negative intermediate values must therefore be produced by binary subtraction between sub-expressions, such as (3-4), (2-(3+4)), or ((1+2)-7), rather than by writing a negative literal such as -1.

  print_result(pass, static_cast<int>(tests.size()));
  return 0;
}
