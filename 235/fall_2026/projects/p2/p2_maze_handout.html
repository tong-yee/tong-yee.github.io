In this project you'll implement three versions of the same core idea — "is there a way to get from one cell of a grid to another?" — using breadth-first search (BFS). Each task builds directly on the one before it: Task A gets BFS working on the simplest possible grid, Task B removes an assumption about the grid's shape, and Task C changes the question from "can I get there?" to "show me exactly how."

What You're Given

Every task uses the same coordinate type:

struct Coordinate {
  int row;
  int col;
};

A maze is a std::vector<std::vector<int>>. A cell value of 0 means the cell is open (you can stand there); any other value means it's blocked. In Tasks A and B, main() already contains several test mazes and calls your function on them. Do not rename the required files, structs, or functions. You may add tests to main(), but do not remove the provided tests.

Key idea: BFS explores in layers Starting from start, BFS visits every cell exactly one step away first, then every cell exactly two steps away, then three, and so on. A queue (FIFO) is what makes this happen automatically: whatever you push now is explored only after everything already waiting in line. This is also why the first time BFS reaches a cell, it has found a shortest path to it — important context for Task C.

Complexity Analysis

For a fixed-width maze, let R be the number of rows and C the number of columns. For a ragged maze there is no single C — instead let V be the total number of cells across all rows combined. The R term matters on its own because a ragged maze can contain many empty rows that BFS still has to skip past.

TaskTimeAuxiliary space
A, fixed width O(RC) O(RC)
B, ragged O(R + V) O(R + V)
C, ragged path O(R + V) O(R + V)

In every case, each cell is pushed onto the queue at most once (guarded by visited), and each cell popped does O(1) work to check its four neighbors, so total work is proportional to the number of cells (plus the row bookkeeping itself, hence the R term for ragged mazes). The visited structure and the queue can each hold up to one entry per cell; Task C additionally allocates one Node per visited cell.

Task A — Reachability on a Fixed-Width Grid (25 pts)

What to implement

Complete bool reachable(const std::vector<std::vector<int>>& maze, Coordinate start, Coordinate target) in maze_v1_fixed_width.cpp. Every row of the maze has the same number of columns for this task — you may assume this. Return true if there is a path of open cells (moving up, down, left, or right, never diagonally) from start to target; return false otherwise.

Must handle correctly

  • An empty maze, or a maze whose rows are empty — return false.
  • start or target outside the grid's bounds — return false.
  • start or target on a blocked cell — return false.
  • start equal to target (and open) — return true immediately; no movement needed.
  • A maze with no path between two otherwise-valid open cells — return false once every reachable cell has been explored.

Key idea — walkthrough

Trace reachable(maze, {0,0}, {3,3}) on this 4×4 maze (0 = open, 1 = wall): 

     0  1  2  3
  0  0  0  1  1
  1  0  0  1  1
  2  0  0  0  1
  3  0  0  0  0

Check neighbors in the order up, down, left, right. For Tasks A and B this order cannot change the true/false answer, but keep it anyway: Task C reuses the exact same traversal, and there neighbor order determines which shortest path gets returned. This project's autograder checks Task C's returned path for an exact match against the up/down/left/right traversal, so consistent ordering matters starting now.

StepDequeueNewly enqueuedQueue after this step
1(0,0)down (1,0), right (0,1)[(1,0), (0,1)]
2(1,0)down (2,0), right (1,1)[(0,1), (2,0), (1,1)]
3(0,1)dead end[(2,0), (1,1)]
4(2,0)down (3,0), right (2,1)[(1,1), (3,0), (2,1)]
5(1,1)dead end[(3,0), (2,1)]
6(3,0)right (3,1)[(2,1), (3,1)]
7(2,1)right (2,2)[(3,1), (2,2)]
8(3,1)right (3,2)[(2,2), (3,2)]
9(2,2)dead end[(3,2)]
10(3,2)right (3,3)[(3,3)]
11(3,3)— matches target, return true[]
Rule of thumb Check curr == targetIdx immediately after dequeuing, before you look at its neighbors. This is what lets BFS stop early: once the target is dequeued, no remaining queued cells or target neighbors need to be processed. Don't "keep exploring until the queue is empty and then check if you visited the target" — that does unnecessary work and, more importantly, is not what the autograder's traces expect.

Task B — Reachability on a Ragged Grid (35 pts)

What to implement

Complete the same-signature reachable() in maze_v2_ragged.cpp, but now rows may have different lengths. A row with zero columns is a completely empty row.

The one bug this task is designed to catch In Task A, you likely used one numCols value for every bounds check. That assumption breaks here. When you consider moving to a neighboring cell, you must check that column against that neighbor's own row length — not the current row's length, and not some maze-wide constant. Moving right within a row checks the current row's length (since the neighbor is in the same row); moving up or down checks the neighbor row's length.

Must additionally handle

  • A maze where every row is empty — still false. (You do not need a special-case loop for this: if every row is empty, start.col >= maze[start.row].size() is automatically true for any non-negative column, so the ordinary bounds check on start already returns false. A separate "are all rows empty?" check is unnecessary because the ordinary start-coordinate validation already handles that case — convince yourself of this before you write one.)
  • start valid for its own row but a neighboring row is shorter — the out-of-range neighbor must be skipped, not accessed.
  • A completely empty row acting as a full barrier between the rows above and below it (there is no column it shares with anything, so nothing can pass through it vertically).

Key idea — walkthrough

Trace reachable(maze3, {0,0}, {4,1}) on this ragged maze (blank = not part of that row at all):

     0  1  2  3
  0  0  1
  1  0  1  1  0
  2  0  0
  3  1  0  0
  4  1  0
StepDequeueNewly enqueuedQueue after this step
1(0,0)down (1,0) — right is blocked by a wall at (0,1)[(1,0)]
2(1,0)down (2,0) — right (1,1) is a wall[(2,0)]
3(2,0)right (2,1) — down (3,0) exists but is blocked[(2,1)]
4(2,1)down (3,1) — right would be column 2, but row 2 has only 2 columns, so it's skipped[(3,1)]
5(3,1)down (4,1), right (3,2)[(4,1), (3,2)]
6(4,1)— matches target, return true[(3,2)]

Notice (3,2) is still sitting in the queue, unexplored, when the function returns. That's correct: BFS doesn't need to finish exploring the whole maze once it's found the target.

Task C — Return an Actual Path (40 pts)

What to implement

Complete std::list<Coordinate> findPath(const std::vector<std::vector<int>>& maze, Coordinate start, Coordinate target) in maze_v3_find_a_path.cpp. Instead of a yes/no answer, return the sequence of coordinates from start to target, inclusive. If no path exists (including any of the invalid-input cases from Tasks A/B), return an empty std::list<Coordinate>.

You're given a second struct:

struct Node {
  Coordinate position;
  Node* parent;
};
Key idea: the queue is secretly building a tree Every time you discover a new cell from curr, that new cell's parent is curr. If you record that link on a Node instead of throwing it away, then once you dequeue the target you can walk parent pointers backward — target → ... → start — and you've reconstructed the exact shortest path BFS found. This is the same "BFS tree" idea from Tasks A/B, made explicit: each layer's cells all point back to the specific parent cell that discovered them.

Given helper functions — do not modify

  • std::list<Coordinate> backtrack(const Node* currPtr) — walks parent pointers from a given node back to the root and returns the path in start → target order. Call this once you dequeue the target.
  • void releaseMemory(std::vector<Node*>& nodePtrVec) — deletes every Node you allocated. backtrack() copies out plain Coordinate values, so it's safe to release every node's memory immediately afterward.
  • void print(...) — the display/formatting harness used by main(). You should not need to touch it.
Memory management is part of this task's grade Every neighbor you discover must be allocated with new Node{...} and pushed into both the BFS queue and a std::vector<Node*> that tracks everything you've allocated. Whether or not you find the target, call releaseMemory() on that vector exactly once before returning — on the "found" path after calling backtrack(), and on the "queue emptied, nothing found" path. Compile and test with sanitizers if you have access to them — a silent memory leak will not show up just by reading the printed output: 
g++ -std=c++17 -Wall -Wextra -Wpedantic \
    -fsanitize=address,undefined \
    -fno-omit-frame-pointer maze_v3_find_a_path.cpp
Leak detection is normally included in AddressSanitizer on supported systems, though this can be environment-dependent.

Key idea — walkthrough

Using the same maze and start/target as the Task B walkthrough (maze3, (0,0) → (4,1)), here is how the parent pointers chain together once (4,1) is dequeued: 

(0,0) <- (1,0) <- (2,0) <- (2,1) <- (3,1) <- (4,1)
  parent of (1,0) is (0,0)
  parent of (2,0) is (1,0)
  parent of (2,1) is (2,0)
  parent of (3,1) is (2,1)
  parent of (4,1) is (3,1)

backtrack() starts at the Node* for (4,1), pushes each position onto the front of the list as it follows parent pointers (so the final order reads start-to-target, not target-to-start). It copies the start node — the node whose parent is nullptr — and stops when the traversal pointer itself becomes nullptr. The resulting path: 

[start](0,0)->(1,0)->(2,0)->(2,1)->(3,1)->(4,1)[end]

Must additionally handle

  • All the same invalid-input cases as Tasks A/B (empty maze, out-of-bounds or blocked start/target) — return an empty list, and make sure you haven't allocated anything yet when you hit these checks.
  • start == target (both open) — the path is the single-element list containing just that coordinate.
  • No leaked or double-freed Nodes on either return path (found or not found).
