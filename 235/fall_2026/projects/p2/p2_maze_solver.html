Project 2: Maze Solver

Inheritance, polymorphism, depth-first search and breadth-first search
Due: see Gradescope

Overview

Imagine you are dropped into a corn maze with a map in your hand. How do you find the exit? There are two classic strategies, and in this project you will build both of them as C++ classes that share one interface.

  • Depth-first search (DFS) is the ball of string strategy. You walk down a corridor as far as it goes. At a dead end you walk back to the last junction and try a different turn. You find a way out, but not necessarily a short one.
  • Breadth-first search (BFS) is the ripples in a pond strategy. You check every cell 1 step from the start, then every cell 2 steps away, then 3, and so on, like a ripple spreading outward. The first time the ripple touches the exit, you have found a shortest way out.

Along the way you will practice three ideas from lecture: an abstract base class with a pure virtual function, polymorphism (code written once in the base class that automatically runs your DFS or your BFS, depending on the object), and the data structures that power the two searches, recursion (the call stack) for DFS and a queue for BFS.

The Big Picture: Class Design

Maze_Solver holds the maze and does the work that every solver shares: it answers reachable() and prints the board with the path. The one thing it cannot do is find a path, because that depends on the strategy. So it declares getPath() as pure virtual (the = 0 in the header). That means two things: you cannot create a plain Maze_Solver object, and a derived class must implement (or inherit an implementation of) getPath() before you can create objects of that class. In this project both DFS_Solver and BFS_Solver supply their own. It is like a remote control: every TV (DFS or BFS) has a Find the exit button, but pressing it makes each TV do something different inside.

Look at how little Maze_Solver::reachable() says: a path exists exactly when getPath() returns a non-empty stack. That code was written before your solvers existed, yet when it runs on a BFS_Solver it uses your BFS. What makes this work is that getPath() is virtual: when reachable() calls getPath(), the call goes to the version belonging to the actual object. (reachable() itself does not have to be virtual for this to happen.) The same is true when you call through a base-class pointer or reference:

BFS_Solver bfs(maze, start, end);   // an ordinary local object
Maze_Solver* solver = &bfs;         // a base-class pointer to it
std::stack<Coord> path = solver->getPath();   // runs BFS_Solver::getPath()
bool ok = solver->reachable();                  // base-class code, which calls BFS_Solver::getPath()

A side note on cleanup: if you create a solver with new and later delete it through a Maze_Solver*, it is the virtual destructor in Maze_Solver that makes C++ run the derived class's destructor as well. You will not need new in this project, but the rule is worth remembering.

How a maze is represented

  • A maze is a std::vector<std::vector<int>>. A 0 is an open cell and a 1 is a wall.
  • Rows may have different lengths. Never assume the maze is a perfect rectangle.
  • A cell is a Coord with a row and a col. The start and the end are Coords too.
  • Maze_Solver::isOpen(maze, cell) answers one question: is this cell inside the maze and open? It returns false for walls and for cells outside the maze, so you never need to check bounds yourself. Use it for every neighbor.
  • You may move one step left, right, up, or down (no diagonals). The four neighbors are left (row, col-1), right (row, col+1), up (row-1, col), and down (row+1, col). DFS must check neighbors in the order left, right, up, down. BFS may use any neighbor order; the worked example uses the same order as DFS.

How a path is returned

getPath() returns a std::stack<Coord>, like a pile of plates. The start cell is on top and the end cell is at the bottom, so popping repeatedly reads the route in walking order. If there is no path, return an empty stack.

Algorithm Reference

Depth-first search

DFS is naturally recursive. A call that is handed a cell first marks it visited. If that cell is the end, the search has succeeded. Otherwise the call tries each unvisited open neighbor in turn, and as soon as one neighbor's call succeeds, this call succeeds too. If every neighbor fails, this call fails and control returns to the caller, which then tries its next neighbor. That return is the “walk back to the last junction” step. Your visited table must live outside the recursive function (pass it by reference), so that all the calls share it.

How a call tells its caller “I succeeded” is up to you. One option is a bool return value. Another is to let the recursion fill the answer stack you are going to return: the call that reaches the end puts the end on it, and each caller that finds the stack non-empty after a recursive call knows its own cell belongs to the route. The trace in Task A uses the second option, so you can watch the route being built while the recursion unwinds, from the end of the maze back toward the start.

Where is the backtracking? In a recursive DFS there is no line of code that says “backtrack.” Each call on the recursion stack is a junction you have not finished with. When a recursive call fails, returning to its caller lets the search try the next neighbor. This is backtracking. Control comes back to the line right after the recursive call, you are standing on that junction again, and the loop simply moves on to the next neighbor. When a call succeeds, the callers instead build the answer stack as they return. The call stack is the ball of string.

helper(cell):
    mark cell visited
    if cell is the end:  push it, return          // success
    for each neighbor, in order:
        if neighbor is open and not visited:
            helper(neighbor)                      // go forward
            if the answer stack is now non-empty: // success came back up
                push cell, return
            // otherwise the call returned empty-handed.
            // THIS is the backtrack: the loop continues with the next neighbor.
    // falling off the end means every neighbor failed:
    // returning here backtracks to our caller

Two things to notice. First, the cell is not un-marked when you backtrack: it stays visited, so no other path wastes time re-exploring the same dead end. Second, nothing is removed from the answer stack when you backtrack, because a failed call never put anything there. No explicit removal from the answer stack is needed in this implementation. The DFS visualizer flags every backtrack step so you can watch it happen.

Breadth-first search

BFS keeps a std::queue<Coord>, a line of cells waiting to be explored. Cells leave from the front of the line, and newly discovered neighbors join the back. That first-in, first-out order is exactly what makes the search spread in rings: every cell 1 step away is ahead of every cell 2 steps away.

Key idea — mark a cell visited when you put it in the queue, not when you take it out.

If you wait until a cell leaves the queue, the same cell can be waiting in line several times (once for each neighbor that discovered it), and each copy then adds its neighbors again. Marking cells when they are discovered prevents duplicate queue entries and repeated processing: each cell enters the queue at most once.

A small example. Suppose cells 1 and 2 are the same distance from the start, and both are neighbors of cell 3. When cell 1 is processed, cell 3 is pushed onto the queue. If cell 3 has not been marked yet, then when cell 2 is processed next, cell 3 is pushed a second time. Marking cell 3 the moment it is first pushed makes cell 2 skip it.

To recover the route, BFS also remembers each cell's parent, the cell that discovered it. A second table with the same shape as the maze works well. When the end is found, you follow parents from the end back to the start. Because the stack reverses order, pushing cells in that end-to-start order leaves the start on top.

Complexity Analysis

Let n be the number of cells in the maze (the total number of entries in all rows).

ResourceDFSBFSWhy
TimeO(n)O(n)Every cell is marked visited at most once, and each visited cell looks at only its four neighbors, a constant amount of work. Total work is proportional to the number of cells.
SpaceO(n)O(n)The visited table has one entry per cell. DFS may also hold up to n recursive calls at once (a long winding corridor). BFS may hold up to n cells in the queue and in the parent table.

Both searches have the same Big-O, yet they behave very differently. DFS can wander a long way around before it stumbles on the exit. BFS promises the fewest steps but needs the extra parent table to remember the route. Big-O tells you how the work grows; it does not tell you which answer you get.

You write getPath() in DFS_Solver.cpp and in BFS_Solver.cpp. Use std::queue from the standard library for BFS (you do not need your own queue class). Name your traversal variable curr.

Helper-function name clash. If you write a free helper function (a recursive DFS helper, for example) and DFS_Solver.cpp and BFS_Solver.cpp each define a helper with the same name and parameters, the linker will stop with multiple definition. Give each helper a distinctive name, or declare it static (or put it inside an anonymous namespace) so that it is private to its file.

A Worked Example

We will follow both searches on this 4 × 4 maze. Start at (0,0), end at (3,3). The autograder uses additional mazes, so this example is yours to study.

col 0 1 2 3 row 0 S . . . row 1 . # # . row 2 # # . . row 3 . . . E

Both searches reach the exit, but DFS returns 9 cells while BFS returns 7. Why? At (2,3) DFS tries left before down, so it steps into (2,2) and then (3,2). From (3,2) it tries left first and explores the dead end through (3,1) and (3,0), backs out to (3,2), and only then reaches (3,3). The cells (2,2) and (3,2) stay in its final route, which is why that route is two cells longer than necessary. BFS never commits to one direction, so it goes straight down from (2,3).

The Four Tasks

Task A — DFS_Solver::getPath() (22 points)

What to implement. Return the route found by depth-first search as a stack with the start on top, or an empty stack if there is no path. Your DFS must try the neighbors in the order left, right, up, down. Because a maze can have several routes, this fixed order is what makes the answer unique, and the autograder compares your route cell by cell with the one that order produces. Notice steps 9–12: from (3,2) the search tries left first, wanders into (3,1) and then (3,0), finds a dead end, and returns two calls back to (3,2). That is the ball of string being wound back up. Nothing was added to the answer stack for those two cells, so they are not part of the route. Step 13 then reaches the destination, where the base case fires immediately: the call does not look at any neighbors.

In steps 14–21 every call on the recursion stack finds the answer stack non-empty and pushes its own cell. When the recursion is finished, the answer stack holds (0,0) → (0,1) → (0,2) → (0,3) → (1,3) → (2,3) → (2,2) → (3,2) → (3,3) with the start on top, which is exactly what getPath() must return.

Try it yourself. Step through the recursion call by call with the DFS step visualizer. It shows the recursion stack, the answer stack, and the call tree, using the maze above and three others. Your DFS must try the neighbors in the order left, right, up, down, and the visualizer follows that order.

Edge cases and what to return

  • If the start cell or the end cell is a wall or outside the maze (a negative row or column, a row past the last one, or a column past the end of that particular row), return an empty stack immediately. isOpen() answers all of these for you.
  • If the maze has no rows at all, there is no path: return an empty stack.
  • If the start equals the end and that cell is open, the path is that single cell.
  • The start must be on top of the stack and the end at the bottom.
  • Mazes can contain loops. If you forget to mark cells visited, your program recurses forever and crashes.
  • Rows can have different lengths, so size each row of your visited table from that row.
  • With the specified traversal order and opposite-corner endpoints, the 30 × 30 open-room test exercises deep recursion. Pass the maze, visited table, and answer stack by reference.

Task B — BFS_Solver::getPath() (33 points)

What to implement. Return a shortest route as a stack with the start on top, or an empty stack if there is no path. When several routes tie for shortest, any one of them is accepted. The autograder checks that your route is legal (starts at the start, ends at the end, every step moves to an adjacent open cell, no cell repeated) and that it has the minimum number of cells. You need a queue, a visited table, and a parent table.

Key idea: tracing BFS by hand

Each row below dequeues one cell, looks at its neighbors in the order left, right, up, down (BFS may use any neighbor order; this worked example uses the same order as DFS), and queues the new ones. The queue is shown front to back. When a neighbor turns out to be the end, we record its parent and stop; the end is never put on the queue, which is why step 7 shows only (2,2) waiting.

StepDequeued (curr)Newly discoveredQueue after the step (front → back)
1(0,0)(0,1) (parent (0,0)), (1,0) (parent (0,0))(0,1) (1,0)
2(0,1)(0,2) (parent (0,1))(1,0) (0,2)
3(1,0)— (nothing new)(0,2)
4(0,2)(0,3) (parent (0,2))(0,3)
5(0,3)(1,3) (parent (0,3))(1,3)
6(1,3)(2,3) (parent (1,3))(2,3)
7(2,3)(2,2) (parent (2,3)), (3,3) (parent (2,3))(2,2)

The cell (1,0) in step 3 has no unvisited open neighbor, so it simply disappears from the line. BFS does not “backtrack”; it just keeps serving the next cell in line.

Key idea: remember who discovered each cell

Whenever you discover a new cell, record its parent: the cell you were standing on. This includes the destination, which your code records but does not need to enqueue. Nothing else is needed to rebuild the route. In the example, following parents from the end gives

(3,3) ← (2,3) ← (1,3) ← (0,3) ← (0,2) ← (0,1) ← (0,0)

Pushing these onto a stack in the order (3,3), (2,3), (1,3), (0,3), (0,2), (0,1), (0,0) leaves (0,0) on top. Cells like (1,0) that were visited but led nowhere have parent chains of their own, but they do not appear in the destination's parent chain, so they are not in the answer.

Try it yourself. Step through a BFS one dequeue at a time with the BFS step visualizer. It draws the queue and the BFS tree as they grow. Its mazes are different from the one above, and it checks neighbors in the order up, down, left, right. DFS must use left, right, up, down. BFS may use any neighbor order; the autograder accepts any legal shortest path, regardless of which equally short route the neighbor order produces.

Why does BFS give the shortest route? Cells leave the queue in order of distance from the start: all the 1-step cells, then all the 2-step cells, and so on. The first time the end is discovered, no shorter route can exist, since a shorter one would have been discovered in an earlier ring.

Edge cases and what to return

  • No path, a wall at the start or end, an endpoint outside the maze, or a maze with no rows: an empty stack.
  • Start equals end and that cell is open: a stack with that one cell. (Check this before the queue loop starts.)
  • Choose an initial “no parent” value that can never be a real cell (for example a negative row), so you know where to stop when walking back.
  • Do not forget to remove each cell from the queue after you take it from the front.
  • Open rooms with loops: marking when you enqueue keeps this fast. Tests are cut off after 5 seconds.

Task D — Integration check: polymorphism through Maze_Solver* (25 points)

What to implement. Nothing new: this is an integration check of everything so far. Task D checks that your two solvers work when they are handled only through the base-class pointer, which is the entire point of polymorphism. The test code stores a DFS_Solver and a BFS_Solver as Maze_Solver* (or std::unique_ptr<Maze_Solver>) and calls getPath() and toString(). Try the same thing in your own main.cpp:

std::vector<std::vector<int>> room = {{0, 0, 0},
                                       {0, 0, 0},
                                       {0, 0, 0}};
Coord start{1, 1};     // the middle of the room
Coord end{0, 1};       // the top middle
DFS_Solver dfs(room, start, end);
BFS_Solver bfs(room, start, end);
Maze_Solver* solvers[]{&dfs, &bfs};
for (const Maze_Solver* curr : solvers) {
  std::cout << curr->toString() << '\n';   // one loop, two different searches
}

Run it and compare the two printed routes: DFS takes four cells, BFS takes two. That is polymorphism in action. The derived toString() adds a heading and then calls the base-class version, which in turn calls the getPath() of whichever object it is running on. Keep every function marked override in the headers; the compiler will then catch a misspelled signature for you.

  • Compile it yourself first: g++ -std=c++17 -Wall -Wextra main.cpp Maze_Solver.cpp DFS_Solver.cpp BFS_Solver.cpp -o maze. Fix every warning. Also run valgrind ./maze before you submit; professional code does not leak memory.
  • Build in the order of the tasks, and test each solver on your own small mazes before you submit.

// Maze_Solver.hpp
#ifndef MAZE_SOLVER_HPP
#define MAZE_SOLVER_HPP
#include <vector>
#include <stack>
#include <string>

struct Coord {
  int row;
  int col;
};

class Maze_Solver {
  public:
    Maze_Solver();
    Maze_Solver(const std::vector<std::vector<int>>& maze, const Coord& start, const Coord& end);

    std::vector<std::vector<int>> getMaze() const;
    Coord getStart() const;
    Coord getEnd() const;

    virtual bool reachable() const;
    virtual std::stack<Coord> getPath() const = 0;
    virtual std::string toString() const;

    virtual ~Maze_Solver() = default;

    // helper function, check whether a Coord object is a valid cell in the maze and is accessable (value = 0)
    static bool isOpen(const std::vector<std::vector<int>>& maze, const Coord& cell);

  private:
    std::vector<std::vector<int>> maze_;
    Coord start_;
    Coord end_;
};
#endif
