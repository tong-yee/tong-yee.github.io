Learning Objectives

This exercise is Classes 9 and 10 in code form. By the end of it you should be able to:

  • implement a link-based stack, recognizing push and pop as Class 8's prepend and removeFront under new names;
  • implement a link-based queue, and explain why a back_ pointer makes enqueue O(1), while a tail pointer is not needed for O(1) stack operations;
  • handle the transitions a two-pointer structure breaks on — empty to one item and one item back to empty;
  • use a stack to solve a problem that counting cannot solve, because the answer depends on order rather than on totals;
  • respect a documented precondition: check empty() before you call top() or front().
One contract, two implementations Both classes here are the linked versions. The array-based stack and the circular-buffer queue from lecture satisfy the same contracts, and nothing that uses a stack or a queue would have to change if you swapped them in. That is the point of an ADT, and it is worth re-reading the Class 9 and Class 10 slides with that in mind before you start.

Task A — Stack::push()

Put value on top of the stack. The top is the front of the chain, so this is one familiar operation under a new name. Keep size_ correct.

push returns bool and should always return true: a linked stack cannot be full. The return type exists so that this class and an array-based stack present the same interface — the array version can fail.

Task B — Stack::pop() and top()

pop() removes the top item and returns false if the stack is empty. top() returns the top item and removes nothing.

pop() frees a node, so the order of your three statements is not a matter of taste. Ask yourself which pointer you still need after the delete, and make sure you have read it before then.

A precondition is a promise the caller makes top() on an empty stack is undefined — the header says so. You do not have to defend against it inside top(), and the tests never call it on an empty stack. What you do have to do is honour that promise everywhere you call top(), which matters in Task E.

Task C — Queue::enqueue()

Add value at the back. The new node always goes at the end, so it is the one whose next is nullptr.

There are two cases, and they differ in which pointer must change. In one of them it is front_ and back_ together; in the other it is a node's own next field, and then back_. Work out which is which before you write either.

In the second case the two writes have a required order. Write them down in the wrong order and read what the code says afterwards: which pointer still reaches the node you just allocated?

Task D — Queue::dequeue() and front()

dequeue() removes the item at the front and returns false if the queue is empty. front() reads it without removing, and carries the same precondition as top().

Start from pop(): the removal itself is identical. Then add the line this class needs and a stack does not — the one you found in warm-up exercise 3.

Why this one is worth the extra minute A queue with a stale back_ passes every test you are likely to write by hand: it is empty when it should be empty, and the size is right. The damage appears on the next enqueue(), which writes into memory that has already been freed — and a program can run for a long time after that before it crashes, somewhere unrelated. This is exactly the class of bug the memory-safety check is for.

Task E — balanced()

Return true when every opening bracket in the string is closed by the matching closing bracket, in the correct order. The three pairs are (), [] and {}. Any other character is ignored completely. The exact cases are in the comment above the declaration in Stack.hpp.

Counting brackets is not enough. "([)]" has two opening brackets and two closing brackets and is still wrong, because when you reach ) the most recent unmatched opening bracket is [, not (. The phrase most recent unmatched is what tells you which container to use.

There are two ways to fail, and your function must catch both: a closing bracket that matches nothing, and an opening bracket that is never closed. One of them is detected inside the loop; the other is only visible after the loop ends. Decide what the stack should look like at that point.

The precondition again When you meet a closing bracket, you want to look at top(). But the string might be ")(", and then the stack is empty. Check empty() first. Getting this wrong costs you Task E and the memory-safety points, because dereferencing a null head_ is an invalid read.

Task F — reverseQueue() (optional practice)

Not graded. You may leave the empty body exactly as it is; it must stay there so the program links.

Reverse a queue in place using a Stack: take everything out of the queue and push it, then pop everything and put it back. It comes out in reverse order because of the stack's LIFO behavior. This is the Class 9 backup slide (“Reversing With a Stack”) applied to a queue, and it is a good way to check whether you understood both structures — it is the only place in this exercise where the two have to cooperate.

Edge Cases to Test

CaseWhat must happenWhat goes wrong if you miss it
Any operation on an empty structure pop() and dequeue() return false and change nothing a null dereference, or a size_ that goes negative
enqueue into an empty queue both front_ and back_ must be set back_->next is written through a null pointer
dequeue the last remaining item back_ must be reset to nullptr the next enqueue() writes into freed memory
Refill after emptying the structure behaves exactly as it did when new a stale back_ or a corrupted head_
balanced("") true — there is nothing to mismatch an empty-stack check written the wrong way round
balanced(")(") false, without crashing top() called on an empty stack

// Stack.hpp
// CSCI 235 -- Exercise 5: Stacks and Queues
// Provided file -- do not modify. Gradescope compiles your submission
// against the original version of this file.

#ifndef STACK_HPP
#define STACK_HPP

#include <string>

// A link-based stack of ints -- the LinkedStack from Class 9.
//
// The top of the stack is the FRONT of the chain, so push() is Class 8's
// prepend() and pop() is Class 8's removeFront(). That is what makes every
// operation O(1): you never walk the list.
//
// head_ points at the top node; the bottom node's next is nullptr;
// head_ == nullptr is the empty stack.
class Stack {
public:
    Stack();       // provided -- head_ = nullptr, size_ = 0
    ~Stack();      // provided -- deletes every remaining node

    // Copying is disabled, for the same reason as in Exercise 4: without a
    // deep copy, two stacks would share one chain and both destructors would
    // delete each node. A compile error is better than a double free.
    Stack(const Stack& other) = delete;
    Stack& operator=(const Stack& other) = delete;

    // ---- Implement these in Stack.cpp ----
    bool push(int value);   // Task A -- always returns true for a linked stack
    bool pop();             // Task B -- false if the stack is empty
    int  top() const;       // Task B -- PRECONDITION: !empty()

    // ---- Provided observers ----
    bool empty() const;            // head_ == nullptr
    int  size() const;             // O(1): the stored count
    std::string toString() const;  // "30 -> 20 -> 10" (top first), or "(empty)"

private:
    struct Node {
        int   data;
        Node* next;
    };

    Node* head_;
    int   size_;
};

// ---- Task E: implement this in Stack.cpp ----
//
// Returns true when every opening bracket in `text` is closed by the matching
// closing bracket, in the correct order. Characters that are not one of
// ( ) [ ] { } are ignored entirely.
//
//   balanced("a(b)[c]")   -> true
//   balanced("{[()]}")    -> true
//   balanced("([)]")      -> false   (closed in the wrong order)
//   balanced("(()")       -> false   (an opening bracket never closed)
//   balanced(")(")        -> false   (a closing bracket, nothing open)
//   balanced("")          -> true    (nothing to mismatch)
//
// Use a Stack. Counting brackets is not enough -- order is what matters.
bool balanced(const std::string& text);

#endif

Queue.hpp — provided, do not modify

// Queue.hpp
// CSCI 235 -- Exercise 5: Stacks and Queues
// Provided file -- do not modify. Gradescope compiles your submission
// against the original version of this file.

#ifndef QUEUE_HPP
#define QUEUE_HPP

#include <string>

// A link-based queue of ints -- the LinkedQueue from Class 10.
//
// Items join at the BACK and leave from the FRONT, so the class keeps two
// pointers. front_ is where dequeue() removes; back_ is where enqueue() adds.
// Both are nullptr when the queue is empty, and both point at the SAME node
// when the queue holds exactly one item.
//
// That one-item case is where this class is usually gotten wrong. Read the
// comments on enqueue() and dequeue() carefully.
class Queue {
public:
    Queue();       // provided -- front_ = back_ = nullptr, size_ = 0
    ~Queue();      // provided -- deletes every remaining node

    Queue(const Queue& other) = delete;
    Queue& operator=(const Queue& other) = delete;

    // ---- Implement these in Queue.cpp ----

    // Task C. Adds `value` at the back. Always returns true.
    //
    // Two cases:
    //   - the queue is empty: the new node is BOTH the front and the back.
    //   - otherwise: hook it onto the current back, THEN advance back_.
    //     (Advance first and back_->next = newNode becomes
    //      newNode->next = newNode -- the new node points at itself and
    //      is never connected to the queue.)
    bool enqueue(int value);

    // Task D. Removes the item at the front. Returns false if empty.
    //
    // This is Class 8's removeFront() plus ONE extra line: when the queue
    // becomes empty, back_ must be reset to nullptr as well. Otherwise back_
    // is left pointing at memory you just freed, and the next enqueue()
    // writes into it.
    bool dequeue();

    // Task D. Reads the front item. PRECONDITION: !empty()
    int front() const;

    // ---- Provided observers ----
    bool empty() const;            // front_ == nullptr
    int  size() const;             // O(1): the stored count
    std::string toString() const;  // "10 -> 20 -> 30" (front first), or "(empty)"

private:
    struct Node {
        int   data;
        Node* next;
    };

    Node* front_;
    Node* back_;
    int   size_;
};

// ---- Task F (OPTIONAL PRACTICE -- not graded) ----
//
// Reverses `q` in place, so that the item that was at the back ends up at the
// front. Use a Stack: dequeue everything into it, then pop everything back
// into the queue. It comes out in reverse order because of the stack's LIFO behavior.
//
// This is the Class 9 backup slide ("Reversing With a Stack") applied to a
// queue -- and it is a good way to check you understood both structures.
void reverseQueue(Queue& q);

#endif

Stack::Stack() : head_(nullptr), size_(0) {}

Stack::~Stack() {
    while (head_ != nullptr) {
        Node* toDelete = head_;
        head_ = head_->next;
        delete toDelete;
    }
    size_ = 0;
}

bool Stack::empty() const {
    return head_ == nullptr;
}

int Stack::size() const {
    return size_;
}

std::string Stack::toString() const {
    if (head_ == nullptr) {
        return "(empty)";

    std::ostringstream out;
    for (Node* curr = head_; curr != nullptr; curr = curr->next) {

// every label is printed in the same 14-character column
static void label(const std::string& text) {
    std::cout << "  " << std::left << std::setw(14) << text << " : ";
}

static void show(const std::string& text, const Stack& s) {
    label(text);
    std::cout << s.toString() << "   (size " << s.size() << ")\n";

    label(text);
    std::cout << q.toString() << "   (size " << q.size() << ")\n";
