Why This Setup

Valgrind — the memory-checking tool we use throughout this course — is a Linux tool. This course supports Valgrind through Linux: native Windows is not supported, and native macOS support is limited and not supported for this course. Since most of you use VS Code on a Mac or Windows laptop, we need a real Linux environment to run it in.

GitHub Codespaces gives you exactly that: a full Linux machine in the cloud, pre-configured with g++, gdb, and valgrind already installed, that opens directly inside VS Code — in your browser, or in your local VS Code app if you prefer. Nothing to install beyond a GitHub account, and it uses your own free monthly Codespaces quota, not anything billed to the course.

What You Need

  • A (free) GitHub account. If you already have one from a previous course or personal projects, that works fine.
  • A web browser. That’s it — no local installs are required for this path.
Free usage A free GitHub account includes 120 core-hours of Codespaces use per month — about 60 hours of running time on the standard 2-core machine, since usage is multiplied by machine size — plus 15 GB of storage. This should cover course use if you stop your codespace when you’re finished (see Coming Back to Your Codespace Later below). Accounts may need a payment method or spending limit on file to continue past the included quota. Each of you uses your own account and your own quota — nothing is shared or billed to anyone else.

Step 1 — Fork the Repository

The workflow you’re learning

Course repository → Fork → your personal GitHub repository → Codespace → edit → git status → git add → git commit → git push

The course repository is the shared starting point everyone forks from. Your fork is your own personal copy of it on GitHub — a real repository that belongs to you. The codespace is a temporary Linux workspace you open on top of your fork; nothing in it is permanent until you save it. commit records a snapshot of your work locally, inside the codespace; push sends that snapshot to your fork on GitHub, where it’s saved for good.

Copy/paste, in the terminal 

cd Buffer
g++ -std=c++17 -g Buffer.cpp main.cpp -o test
valgrind --leak-check=full ./test

For the buggy grow() from lecture, you should see Valgrind report definitely lost: 16 bytes in 1 blocks — the same leak from the lecture slip. This is the general pattern you’ll use for every exercise and project that asks you to check your work with Valgrind: compile with -g (so Valgrind can point to line numbers), then run the program through valgrind --leak-check=full instead of running it directly.

Reading the Report

The relevant part of the output looks like this:

==12345== HEAP SUMMARY:
==12345==     in use at exit: 16 bytes in 1 blocks
==12345==   total heap usage: 3 allocs, 2 frees, 73,776 bytes allocated
==12345==
==12345== 16 bytes in 1 blocks are definitely lost in loss record 1 of 1
==12345==    at 0x...: operator new[](unsigned long)
==12345==    by 0x...: Buffer::Buffer(unsigned long)
==12345==    by 0x...: main
Ignore the totals, trust the leak summary total heap usage counts every heap allocation in the whole program — including ones the C++ runtime itself makes on startup that have nothing to do with your code. Don’t try to match that number against your own new calls. The line that matters is definitely lost: that is a genuine leak — memory nothing in your program can reach anymore.

Now look closely at the stack trace under definitely lost. It points at Buffer::Buffer(unsigned long) — the constructor — not at grow(). That can be confusing, since the constructor didn’t do anything wrong. What Valgrind is telling you is where the lost block was allocated, not which function is responsible for losing track of it. Those are often different functions, and telling them apart is the real skill here:

  1. Check the size. 16 bytes is four ints — that matches Buffer(4)’s array, not grow(8)’s (which would be 32 bytes). So the block that went missing is the original array from the constructor.
  2. Search your class for every place that pointer gets reassigned. Look for data_ = throughout Buffer.cpp. It happens in exactly one place outside the constructor: grow().
  3. That reassignment, with no delete[] first, is the actual bug — even though grow() never appears anywhere in the stack trace.
The general method Valgrind always names the allocation site for a lost block. It’s on you to trace forward through the code from there and find where that same pointer gets overwritten without being freed first — that function is the one actually responsible for the leak. You’ll use this exact reasoning on every project this semester, not just this demo.

Save Your Work

Files in your codespace are not automatically backed up anywhere else. This is also your first real practice with the everyday git workflow you’ll use all semester: check what changed, stage it, commit it with a message, and push it to GitHub. Take the extra minute here — this loop is worth more than any single exercise.

Copy/paste, in the terminal 

cd Buffer
git status
git add Buffer.hpp Buffer.cpp main.cpp .gitignore
git commit -m "Complete Buffer exercise"
git push

git status shows what’s changed. git add stages the files you want in the next snapshot. git commit records that snapshot locally, with a message describing what you did. git push sends it to your fork on GitHub.

Now confirm it actually landed there: go to your fork’s page in the browser, refresh it, and click Commits (near the top of the file list, next to the branch selector). You should see the exact commit message you typed. Seeing your own commit show up on GitHub — not just a clean terminal — is the real confirmation your work is saved.

Codespaces are not permanent storage An idle codespace may be automatically deleted after a period of inactivity (up to 30 days by default), including any work you never pushed. Get in the habit of committing and pushing before you stop working, not just before a deadline.

Reference: Codespace retention
The codespace and your fork are not the same thing Each codespace you create gets its own random, disposable name — something like cs235_program_f26 [fuzzy carnival], shown in the Explorer panel. That name refers only to this one running container. If that codespace is deleted (or you delete it yourself), only that container and anything unpushed inside it disappear. Your fork on GitHub — and any commits you pushed to it — is a separate, permanent thing that isn’t affected. You can always create a brand-new codespace (with a different random name) from your fork, and it will start with whatever you last pushed.

Coming Back to Your Codespace Later

Reopen the same codespace to continue working — go to github.com/codespaces to see your existing ones. Reopening preserves any unpushed files for as long as that codespace still exists. But commit and push regularly anyway: if that codespace is later deleted, a new codespace you create afterward will not automatically include unpushed work — only what you’ve already pushed to your fork survives.

Stop your codespace when you’re done, rather than just closing the browser tab — closing the tab does not stop it. From github.com/codespaces, click the “…” next to a running codespace and choose Stop codespace. This is what keeps you within your free monthly quota.

Troubleshooting

My browser URL shows the instructor’s username, not mine This means you created a codespace directly on the original course repository instead of your fork — you’ll be able to run Valgrind, but git push won’t work the way this guide describes. Delete that codespace from github.com/codespaces, go back to Step 1, and make sure you land on your fork before creating a codespace.
valgrind: command not found This means your codespace wasn’t built from the course’s dev container configuration — most likely you're in a codespace created before the setup was fixed, or on a different repository. Delete that codespace from github.com/codespaces and create a fresh one from your fork following Step 2 again.
“This codespace is running in recovery mode” This means the container failed to build. Delete the codespace and create a new one. If it happens again, post on the course forum or email the instructor with a screenshot of the error — don’t spend more than a few minutes troubleshooting it yourself.
Codespace seems slow or won’t load Try a hard refresh of the browser tab. If that doesn’t help, close the tab, go back to github.com/codespaces, and reopen it from there.

If you run out of free Codespaces hours, or your account can’t create one for some reason, the same environment also runs locally through Docker Desktop plus VS Code’s Dev Containers extension — free, with no hour limit, using the exact same configuration file.
